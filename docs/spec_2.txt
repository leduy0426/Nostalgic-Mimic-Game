1. Context &amp; Goal
1.1 Business Problem
Existing casual-game websites and digital versions of nostalgic games already serve players. This project does not claim to invent Number Hunt or Caro or to be the first platform with avatars and leaderboards. Instead, it explores whether a focused experience combining recognizable childhood games, minimal friction to begin playing, short and satisfying sessions, immediate results, easy replay, and shared avatar/achievement progression can appeal to students and young adults. Remote play with a friend adds a social dimension. The relative importance of these needs and the appeal of the combination are hypotheses requiring user testing. [CONFIRMED — Ideation §§1–2]
1.2 Product Goal
The system will provide a responsive browser-based game hub, prioritizing an operational Number Hunt game in both Solo and PvP modes. A registered player can save personal results and advance one basic avatar with XP and levels. The gameplay itself remains the primary entertainment value; avatar progression adds long-term identity rather than a separate pet-care simulator. [CONFIRMED — Ideation §§1, 4, 7–8]
The product strategy is Attract → Engage → Return &amp; Share: nostalgia is a possible discovery hook; quick, replayable gameplay is the core experience; records/avatar progression and optional public achievement cards create ways to return and share. This is an intended strategy, not a validated behavioral outcome. [CONFIRMED — Ideation §13]
1.3 Success Criteria and Evidence
For the minimum release, confirm that a real user can reach the Number Hunt game, complete a Solo run, finish a synchronized 2-player PvP match, view the outcome, and start another game. A registered user's authorized record, match result, XP/level and basic avatar data must persist. The project will aim to recruit 50–100 test users as a provisional goal, not an observed result or mandatory grading threshold. [CONFIRMED — Ideation §§8, 11]
Measurements to collect where feasible: steps/time to first game; complete games per session; Play Again usage; clarity of outcome; seven-day return rate if the observation period permits; player interview feedback on nostalgia; optional achievement-card exports if the extended feature is built. [CONFIRMED as proposed measures — Ideation §11]
1.4 Technical Context and Constraints
Four students have 4–8 weeks and experience spanning .NET and Node.js. Frontend, backend, database, hosting, and authentication implementation are TBD; no framework is mandated here. Real-time communication is necessary for PvP, but this document does not assume a particular protocol until architecture selection. The team applies SDD to constraints, behavioral rules and acceptance tests, and ADD to assisted implementation with human review. [CONFIRMED — Ideation §9]

3. Functional Requirements (EARS-style)
Reading guide: WHEN ... THE system SHALL ... defines observable event-driven behavior. Every requirement has an ID, scope and source/decision state.
3.1 Discovery &amp; Game Hub
FR-HUB-01 [CORE, CONFIRMED]: THE system SHALL provide a responsive game hub listing mini games that have been implemented and made available.
FR-HUB-02 [CORE, PROPOSED]: WHEN a visitor selects an available game, THE system SHALL display that game's supported modes and a clear action to start.
FR-HUB-03 [CORE, PROPOSED]: WHEN a game is not included in the deployed build, THE system SHALL NOT present it as playable; it MAY label it as coming soon.
3.2 Accounts &amp; Player Identity
FR-AUTH-01 [CORE, CONFIRMED]: THE system SHALL support a basic user authentication capability so registered players can retain persistent progress.
FR-AUTH-02 [CORE, PROPOSED]: WHEN a player authenticates successfully, THE system SHALL associate subsequent saved records, match results and XP with that player's account.
FR-AUTH-03 [CORE, PROPOSED]: WHEN an unauthenticated person requests private account data, THE system SHALL deny the request without disclosing the data.
FR-AUTH-04 [CORE, TBD]: Guest gameplay eligibility, guest-to-account migration, credential mechanism, password recovery and account deletion workflows require decisions before implementation.
3.3 Number Hunt — Shared Rules
FR-NH-01 [CORE, CONFIRMED]: WHEN a new Number Hunt board is created, THE system SHALL generate a random arrangement containing each integer from 1 through 25 exactly once.
FR-NH-02 [CORE, CONFIRMED]: WHILE a Number Hunt game is active, THE system SHALL recognize numbers in ascending order, starting from 1 and progressing through 25.
FR-NH-03 [CORE, PROPOSED]: WHEN an input does not match the current required number, THE system SHALL not advance the target or award a point.
FR-NH-04 [CORE, PROPOSED]: WHEN a board has finished, THE system SHALL reject subsequent gameplay inputs as state-changing actions.
3.3.1 Solo
FR-NHS-01 [CORE, CONFIRMED]: WHEN a player starts Number Hunt Solo, THE system SHALL display a newly arranged 1–25 board and start tracking the completion time.
FR-NHS-02 [CORE, CONFIRMED]: WHEN the player selects the next required number, THE system SHALL advance the required number until 25 has been selected.
FR-NHS-03 [CORE, CONFIRMED]: WHEN 25 is selected validly, THE system SHALL end the run, show the elapsed time and compare it with the authenticated player's stored personal best.
FR-NHS-04 [CORE, PROPOSED]: WHEN an authenticated player finishes a faster valid Solo run than their stored personal best, THE system SHALL update that record exactly once.
FR-NHS-05 [CORE, TBD]: Whether a Solo timer can be paused, how background tab time is handled, and how unverified/offline scores are treated are unresolved.
3.3.2 PvP (simultaneous, not turn-based)
FR-NHP-01 [CORE, CONFIRMED]: THE system SHALL support a Number Hunt PvP room for two players who see the same board arrangement.
FR-NHP-02 [CORE, CONFIRMED]: WHILE a PvP match is active, both players SHALL be allowed to attempt the current required number simultaneously; there are no alternating turns.
FR-NHP-03 [CORE, CONFIRMED]: WHEN a player is first to successfully claim the current valid number under the system's authoritative ordering rule, THE system SHALL award that player one point and advance the target to the next number. The same player MAY claim consecutive numbers.
FR-NHP-04 [CORE, PROPOSED]: WHEN competing submissions target the same number, THE system SHALL resolve them atomically so that at most one point is awarded for that number; it SHALL publish the accepted target and scores to both clients.
FR-NHP-05 [CORE, CONFIRMED]: WHEN all numbers 1–25 have been claimed, THE system SHALL end the match and identify the winner as the player with the higher total score.
FR-NHP-06 [CORE, PROPOSED]: WHEN the final scores are equal, THE system SHALL declare a draw rather than fabricate an additional scoring rule. Needs approval: a 25-point match cannot end tied if exactly one point is awarded per number, so this clause is a defensive fallback, not an expected normal outcome.
FR-NHP-07 [CORE, PROPOSED]: WHEN a player receives an authoritative state update, THE client SHALL display the accepted next target and current scores without relying on its own speculative award.
FR-NHP-08 [CORE, TBD]: Room creation and invitation method (link/code), room readiness/start, disconnect grace period, reconnect rights, abandonment and forfeit rules require approval.
FR-NHP-09 [CORE, TBD]: Define exactly how simultaneous attempts are ordered (e.g., atomic arrival order at the server), including disclosure of the latency trade-off, before approval. A player's local click timestamp must not be treated as trustworthy proof of being first.
3.4 Post-game, Replay and Records
FR-RES-01 [CORE, CONFIRMED]: WHEN a supported game finishes, THE system SHALL display an outcome appropriate to that mode (Solo elapsed time/personal best or PvP scores/winner).
FR-RES-02 [CORE, CONFIRMED]: WHEN a game has finished, THE result screen SHALL provide an obvious Play Again option that starts a new valid session or rematch flow.
FR-RES-03 [CORE, CONFIRMED]: WHEN an authenticated player finishes a valid game, THE system SHALL maintain applicable results and records persistently.
FR-RES-04 [CORE, PROPOSED]: WHEN the player refreshes the result view, THE system SHALL not award XP again for the same completed match/run.
FR-RES-05 [CORE, TBD]: PvP rematch requires opponent acceptance or a new room? Define before implementation.
3.5 Avatar &amp; XP
FR-AV-01 [CORE, CONFIRMED]: THE system SHALL provide registered players with one basic persistent avatar and a recorded XP/level progression state.
FR-AV-02 [CORE, CONFIRMED]: WHEN an eligible completed game result is accepted, THE system SHALL apply an XP reward according to a documented, approved reward table.
FR-AV-03 [CORE, PROPOSED]: THE system SHALL compute the player's level from a consistently applied progression rule and display the current XP/level to that player.
FR-AV-04 [CORE, PROPOSED]: THE system SHALL store and apply each eligible gameplay reward at most once per verified completion identifier.
FR-AV-05 [CORE, TBD]: XP per activity, leveling thresholds, abuse limits, and whether losses/draws award XP are not yet agreed. Do not generate fixed numerical values without approval.
3.6 Extended Features (only if team chooses to implement)
FR-CARO-01 [EXTENDED, CONFIRMED at concept level]: THE system SHALL support two-player Caro with turn-based placement and determination of the match result. [TBD]: board dimensions, exact line/win rules, overlines, blocked-ends, draws, timer and rematch policy.
FR-MEM-01 [EXTENDED, CONFIRMED at concept level]: THE system SHALL support Solo Memory Matching with paired hidden cards, revealing cards and reporting completion time and attempts. [TBD]: board size, mismatch delay, invalid actions and scoring conventions.
FR-COIN-01 [EXTENDED, CONFIRMED at concept level]: Eligible play MAY award non-monetary Coins redeemable for basic cosmetic customization. [TBD]: amounts, purchase rules and item catalog.
FR-LB-01 [EXTENDED, CONFIRMED at concept level]: The platform MAY provide comparative leaderboards for relevant verified records. [TBD]: privacy and tie-breaking.
FR-SHARE-01 [EXTENDED, CONFIRMED at concept level]: WHEN a player chooses to generate an achievement card, THE system SHALL prepare a card with approved public nickname, avatar, game and verified record, suitable for saving/export. Publishing through social-network APIs is FUTURE.
FR-SHARE-02 [EXTENDED, PROPOSED]: THE system SHALL avoid including email, account identifier, private gameplay metadata or other non-public personal details in exported cards.

7. Acceptance Criteria (Given / When / Then)
The following scenarios form the starting validation baseline. Criteria involving proposed decisions are draft acceptance tests, not proof those decisions were approved.
AC-HUB-01 — Find and launch Number Hunt [CORE]
Given the deployed game hub is open, when a user selects Number Hunt and an available mode, then the appropriate playable screen opens without requiring application installation.
AC-NHS-01 — Correct Solo board [CORE]
Given a new Solo run, when the board appears, then it contains each integer 1 through 25 exactly once and the initial required value is 1.
AC-NHS-02 — Reject incorrect Solo input [CORE, PROPOSED]
Given a Solo run whose required number is 4, when the player selects 6, then the required number remains 4 and no score or completion state changes.
AC-NHS-03 — Finish Solo and record personal best [CORE]
Given an authenticated player has completed numbers 1–24, when the player selects 25, then the run ends, a completion time appears, and a faster verified result becomes the stored personal best. Refreshing does not duplicate the completion reward.
AC-NHP-01 — Identical boards [CORE]
Given two players join the same Number Hunt PvP match, when the match begins, then both see the same numbers in the same positions and a common initial target of 1.
AC-NHP-02 — Competing actions [CORE, PROPOSED]
Given the shared next target is 7 and the score sum equals 6, when both players submit valid claims for 7 concurrently, then the authoritative match accepts exactly one claim, the new score sum is 7, and both clients show target 8 and identical scores.
AC-NHP-03 — Non-turn-based competition [CORE]
Given a player's claim for 10 was accepted, when that player successfully claims 11 before the other player, then the same player receives points for both; no turn alternation is required.
AC-NHP-04 — End of PvP match [CORE]
Given numbers 1–24 were claimed, when number 25 is accepted, then the match ends, final total awarded points equal 25, both clients see the same winner and scores, and further clicks cannot change the outcome.
AC-RES-01 — Quick replay [CORE]
Given a completed Solo game, when the player selects Play Again, then a new game begins and the previous game's saved result remains unchanged.
AC-AV-01 — Avatar persists [CORE]
Given an authenticated player has verified saved XP/level, when the player logs out and logs in again, then the player's avatar and recorded progression remain associated with the same account.
AC-AV-02 — Reward idempotence [CORE, PROPOSED]
Given a verified completion has already applied its XP transaction, when its completion message is delivered again, then the player's XP balance does not increase a second time.
AC-SHARE-01 — Public achievement only [EXTENDED]
Given a user explicitly requests an achievement card for a verified record, when the card is generated, then it includes only the approved public nickname, avatar, game and achievement fields, and excludes private credentials/contact information.
AC-UX-01 — Observe quick-play usability [CORE]
Given a user-testing session, when a participant finds a game, completes one round and optionally selects Play Again, then the team records steps/time to first play, task success, result comprehension and observed voluntary replay. Numeric pass thresholds are TBD.
Additional test suites required before approval: Security/authorization, account lifecycle, losing connectivity, multi-device concurrent sessions, session expiration, load and browser compatibility, as applicable to the approved scope.

8. Out of Scope
The following are excluded from the Core MVP:
Caro PvP, Memory Matching Solo, Coins/cosmetics, public leaderboard and downloadable/shareable achievement cards — EXTENDED if capacity allows.
Dots and Boxes, Stack Tower, Sudoku, AI opponents, random matchmaking, a social friends network, direct social-network API posting, advanced analytics and an extensive cosmetic library — FUTURE.
Full virtual-pet simulation (feeding, hunger, sleep, bathing, multi-stage evolution); real-money currency/transactions; punitive daily streaks or inactivity penalties — not intended for the initial product direction.
A universal mandatory play-time limit applied to every game — explicitly excluded.
